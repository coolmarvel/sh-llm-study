# 문서 작성 가이드

`docs/` 문서를 작성·관리하는 기준. 신규 문서를 만들거나 기존 문서를 갱신할 때 이 규칙을 따른다.

이 프로젝트의 문서는 **사람과 AI 에이전트가 동시에 사용**한다는 전제로 쓴다.
받는 사람(또는 AI)의 사전 지식을 가정하지 말고, 누가 받아도 바로 작업 가능한 형태를 목표로 한다.

## 이력의 SSOT

- **"무슨 일이 언제 있었나"의 SSOT = `docs/session-log.md`**, 커밋/푸시는 사용자가 직접·성긴 단위로
  하므로 git history 를 이력 SSOT 로 삼지 않는다.
- `todo.md` 는 **미해결·향후 작업만** 담는다. 완료분은 session-log 로.
- 세션이 끝날 때 반드시 `session-log.md` 최상단에 그 세션 블록을 추가한다.

## 폴더 구조 (4구역 모델)

| 위치 | 답하는 질문 | 예 |
|---|---|---|
| `docs/` 루트 | 프로젝트 전반, 이력·할 일·릴리스·브리프·작성 규칙 | session-log, todo, brief |
| `docs/adr/` | **왜** 이렇게 결정했나 (대안·트레이드오프) | `0002-stack.md` |
| `docs/plans/` | **무엇을·어떤 순서로** 만들 것인가 (forward-looking) | `0001-mvp.md` |
| `docs/guides/` | **현재 구현된** 동작·코드 위치 | 기능별 가이드 |

기능이 실제 구현되어 코드가 진실이 되면 내용은 `guides/` 로 옮기고 plans 에는 체크 표시만 남긴다.

## 파일명 규칙

- **영어 kebab-case**: `session-log.md`, `approval-workflow.md`
- ADR·plans 는 `NNNN-kebab-title.md` (4자리). 접두/접미어 금지 (`_v2`, `_final`, `GUIDE_` 등)

## 문서 템플릿 (guides)

```markdown
---
title: 문서 제목
created: YYYY-MM-DD
updated: YYYY-MM-DD
domain: <아래 표에서>
---

# 문서 제목

## 개요
무엇을, 어떤 문제를 해결하는지 1~3문단.

## 동작 방식
현재 구현된 동작. 필요 시 데이터 흐름.

## 사용 방법
사용자 관점 설명(해당 시).

## 관련 코드
주요 파일 경로를 1:1 대조 가능하게 (`src/…/file.ts:42`).
```

`domain` 값:

| 값 | 범위 |
|---|---|
| `book` | 교재 챕터 (`docs/book/`) |
| `model` | 토크나이저·모델·학습·생성 코드 동작 |
| `data` | 코퍼스·체크포인트·실험 로그 규약 |
| `dashboard` | 웹 대시보드 (API·화면) |
| `development` | 프로젝트 운영 (세션 로그·todo·검증·하네스) |

ADR 은 `domain` 대신 `status`(`proposed`/`accepted`/`deprecated`/`superseded`)를 쓴다. `adr/0000-template.md` 참고.

## 작성 원칙

1. **현재 코드 기준으로만**, 구현된 것만 적는다. 향후 계획은 `todo.md`/`plans/`로. 코드가 바뀌면 문서와 `updated`도 갱신. 코드와 어긋난 문서는 없느니만 못하다.
2. **SSOT 명시**, 같은 사실을 두 곳에 적지 않는다. 한쪽이 권위를 갖고 나머진 링크.
3. **파일 경로·식별자를 풍부하게**, `src/…/file.ts:71` 형태로. AI 가 grep·Read 로 바로 찾게.
4. **불변·계약을 명문화**. "이 값의 소유권은 X, Y 는 변경 금지" 같은 조건은 분명히. 부수효과를 빠뜨리지 않는다.
5. **함정·과거 사고는 1줄로 보존**, 룰의 근거가 된 사고는 한 줄로. 다음 사람/AI 가 룰을 함부로 깨지 않게.
6. **충실하되 군더더기 없이**, 반복 금지. 코드는 핵심만 발췌. ❌금지/✅권장 표 선호.
7. **튜토리얼 톤 배제**, 사실·계약·경로 위주.

## 교재(`docs/book/`)·노트북: 상세함의 기준 (사용자 피드백 2026-09-16: "너무 당연하다는 듯이만 적혀 있다")

독자는 **LLM 을 처음 배우는 자바 개발자**다. "당연히"·"그냥"으로 넘어가는 문장은 없어야 한다. 장마다 다음을 둔다.

| 절 | 내용 |
|---|---|
| 읽기 전에 | 이 장에 필요한 선수 지식 2~4개와 어느 장에서 배웠는지 |
| 핵심 용어 | 표: 용어 · 한 줄 정의 · 자바/일상 비유. 처음 나오는 용어는 본문에서 **굵게** |
| 단계별 예시 | 3~5 토큰짜리 **손으로 계산할 수 있는 숫자 예시**를 shape 와 함께 끝까지 따라간다 |
| 자바 개발자의 눈으로 | 같은 개념을 자바 코드·자료구조로 대응 (`Map`, `double[][]`, 인터페이스…) |
| 흔한 오해 | "…라고 생각하기 쉽지만 실제로는 …" 2~4개 |
| 스스로 점검 | 답을 말로 할 수 있어야 하는 질문 4~6개 (답은 본문 안에 있어야 한다) |

노트북은 코드 셀 사이의 설명 셀이 **왜 이 셀을 실행하는지 · 출력에서 무엇을 봐야 하는지 · 값을 바꾸면 무엇이 달라지는지**를 말한다.
"해 보기" 셀(값을 바꿔 실행)을 장마다 1개 이상 둔다. 수식은 반드시 같은 계산을 코드로도 보인다.

## 포함하지 않는 것

- AI 와의 대화 로그, 구현 완료 보고서 서술 (→ `session-log.md` 한 블록으로 압축)
- 해결된 트러블슈팅 장문 기록 (근거만 1줄로 ADR/가이드에)
- 테스트 출력·스크린샷 원본

## 언어

- 본문 한국어. 코드·명령어·기술용어·고유명사·파일명·URL 은 영어 원문 유지.
- **줄표(, ) 를 쓰지 않는다** (사용자 피드백 2026-09-16: "AI 같고 안 예쁘다"). 장 제목은 `1장 글자를 숫자로`, 절 제목은 `1.1 토큰화: 모델은 문자열을 모른다`, 본문의 삽입구는 쉼표·괄호·마침표로. 가운뎃점(·)은 나열에만.

## 문서 추가·갱신 절차

1. 알맞은 위치(`docs/` 루트 / `guides/` / `adr/` / `plans/`)에 파일 생성
2. 템플릿·원칙에 맞춰 작성
3. `created`(신규)/`updated`(수정) 날짜 갱신
4. 코드와 1:1 대조, 언급한 파일·함수·경로가 실제 존재하는지 확인
5. `CLAUDE.md` 문서 인덱스에 누락 없는지 확인
