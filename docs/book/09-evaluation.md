# 9장 — 평가: 잘 됐는지 어떻게 아나

생성문을 눈으로 보는 것은 비교가 안 된다(1장). 이 장의 질문은 **모델을 숫자 하나로 비교하는 올바른 방법**, 그리고
**크게 만들면 좋아지는가**다. 노트북 `notebooks/09-evaluation.ipynb`, 코드 `src/shllm/eval.py`.

## 9.1 세 가지 숫자

| 숫자 | 식 | 뜻 |
|---|---|---|
| loss (nat/토큰) | −mean log P(정답) | 학습이 줄이는 그 값. 같은 토크나이저끼리만 비교 |
| perplexity | exp(loss) | "매 순간 몇 개 중 하나를 찍는 셈인가". 균등 찍기면 V |
| bit/글자 | loss · (토큰 수 / 글자 수) / ln 2 | 같은 텍스트를 이 모델로 부호화할 때 글자당 비트. **토크나이저가 달라도 비교 가능** |

**토큰당 loss 는 토크나이저가 다르면 비교할 수 없다.** 문자 2-gram 의 3.1 과 BPE 2-gram 의 7.7 은 "한 글자"와 "두 글자
남짓"을 맞히는 어려움의 차이일 뿐이다. 텍스트는 같으니 **글자당**으로 환산하면 공정하다 (`bits_per_char`).

`evaluate_loss` 는 시드를 고정한 무작위 배치 여러 개의 평균이다 — 모델끼리 **같은 배치**로 비교해야 잡음이 상쇄된다.

## 9.2 지금까지의 모델을 한 표에 (노트북 §1)

같은 val 텍스트(12만 4천 글자)에서 (2026-09-16):

| 모델 | val loss/토큰 | perplexity | bit/글자 |
|---|---|---|---|
| 2-gram (문자, 세기) | 3.20 | 24.5 | 4.61 |
| 3-gram (문자, 세기) | 2.88 | 17.8 | 4.15 |
| 2-gram (BPE, 세기) | 7.67 | 2,145 | 4.84 |
| GPT tiny-notebook (1.4M, 600 스텝) | 6.38 | 587 | 4.02 |
| **GPT small-cpu (6.8M, 2,100 스텝)** | 5.51 | 247 | **3.48** |

토큰당 loss 로는 문자 3-gram(2.88)이 GPT(5.51)보다 "좋아 보이지만" 단위가 다르다. 글자당 bit 로 보면 GPT 가 3.48 로 가장
낮다 — 같은 글을 25% 적은 비트로 부호화한다. 참고로 영어 대형 모델은 글자당 1 bit 근처이고, 우리 모델은 데이터가 49만
토큰뿐이라 여기서 멈춘다.

## 9.3 모델 크기 vs 손실 — 스케일링 맛보기 (노트북 §2)

같은 데이터·같은 스텝(400)으로 크기만 네 단계로 바꿔 학습한다 (`scaling_experiment`):

| 층 · 폭 | 파라미터 | val loss (400 스텝) |
|---|---|---|
| 1 · 64 | 0.57M | 7.25 |
| 2 · 128 | 1.45M | 6.69 |
| 4 · 128 | 1.84M | 6.75 |
| 4 · 256 | 5.26M | 6.46 |

대체로 파라미터가 늘수록 같은 스텝에서 loss 가 낮다 — **큰 모델이 더 빨리 배운다.** 스케일링 법칙(Kaplan et al. 2020)이 말하는
것의 축소판이다. 예외 하나: 같은 폭에서 층만 2→4 로 늘린 모델은 짧은 학습에서 오히려 조금 나쁘다. 깊이는 출발이 느리고,
짧은 학습에서는 **폭**이 더 효율적이다.

단, 데이터가 고정이면 어느 크기부터는 과적합이 더 빨리 올 뿐 **val 최저는 좋아지지 않는다** (7장). 실제 스케일링은
모델·데이터·계산을 **함께** 키운다 (Chinchilla: 파라미터 1개당 토큰 약 20개). 우리 49만 토큰에 맞는 크기는 2~3만
파라미터라는 뜻이고, 6.8M 은 이미 데이터 대비 300배 크다 — 그래서 dropout 과 early best 에 기대는 것이다.

## 9.4 어휘 크기 — 4,096 vs 8,192 (노트북 §3)

2장에서 미뤄 둔 결정. 같은 모델(2층·C=128)을 두 토크나이저로 같은 스텝 학습하고 글자당 bit 로 비교한다.
토큰당 loss 만 보면 어휘가 작은 쪽이 항상 유리해 보인다(맞힐 후보가 적으니). 글자당 bit 로 보면 차이가 줄거나 뒤집힌다 —
어휘가 크면 같은 문맥 창에 더 많은 글자가 들어가고 스텝당 더 많은 글자를 학습하기 때문이다. 대신 임베딩 표가 커진다.

| 어휘 | 코퍼스 토큰 | 파라미터 | loss/토큰 | bit/글자 |
|---|---|---|---|---|
| 4,096 | 666,787 | 0.92M | 5.65 | 4.46 |
| **8,192** | 542,279 | 1.45M | 6.69 | **4.22** |

토큰당 loss 는 4,096 이 낮지만 글자당 bit 는 8,192 가 낮다. **결정**: 이 프로젝트의 어휘는 **8,192 로 유지**한다
(`data/tokenizers/bpe-8192.json`). 토크나이저를 바꾸면 모든 체크포인트가 무효가 되므로 v1 동안 바꾸지 않는다.

## 9.5 평가가 말해 주지 않는 것

loss 는 "확률을 얼마나 잘 맞히나"이지 "글이 얼마나 읽을 만한가"가 아니다. 두 모델의 loss 가 0.1 차이일 때 생성문의
차이는 눈에 안 띌 수도, 클 수도 있다. 대형 모델 평가에 벤치마크(지식·추론 문제 세트)와 사람 평가가 따로 있는 이유다.
이 프로젝트의 v1.0 성공 기준("말이 되는 문단")은 8장에서 눈으로 판정한다.
